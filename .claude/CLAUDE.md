# Executing complex tasks
For tasks with more than 3 steps (or those that need to be broken down), please plan and generate a task list. At each stage reassess your progress through the task list, adjust the task list itself if needed, plan next steps, execute. Perform OODA loops. Keep specific and detailed plans in misc/. Update docs on major milestones.When all outstanding tasks are done, step back and reassess where you are in terms of a plan that's level above. Prioritize next steps.
# Committing and pushing code to git
Commit at key stages. Use short commit messages (<300 chars), explaining the essence of what was done. Don't add your own signature.
# Visuals
This project involves imaging analysis. When relevant, at major stages produce example visuals. Use compact style, clearly labeling key layout elements (e.g. rows, columns). Stick to consistent graphical styles (per instructions). For microscopy stainings, I prefer DAPI in reddish colors, membrane stains in greenish.
# Visual fidelity regression checks
Realistic rendering is the central deliverable. Whenever you change anything that can affect the renderer, training recipe, bundle writer, or inference pipeline, treat it as a regression candidate. Before declaring the change a win, compare the new output at the same scene against both the real reference and the prior known-good artifact — visually AND quantitatively (per-channel intensities at sensible quantiles). If anything got dimmer, blurrier, or lost cell-edge structure relative to what previously worked, that's a blocker. Fix the recipe so any future bundle benefits — don't ship a model snapshot as the workaround.
# Performance regression checks
Same rule for runtime. Before integrating a new feature into any hot path (per-tile, per-cell, per-pixel), measure its cost in isolation first — a small smoke test that times the unit of work and compares to the existing baseline. If integration would multiply a hot-path cost (per-tile I/O re-read, per-cell encoder pass, per-pixel Python loop), use cached / batched / shared infrastructure already in the codebase rather than adding fresh work. Don't ship integration before perf verification at realistic scale.
# Disk space hygiene
Each full bundle write consumes ~20–35 GB under /tmp. Before launching anything that writes a bundle (whole-bundle `xesim explain`, training crop dumps, large stitch jobs) check `df -h /tmp /workspace ~` and warn if free space is under ~50 GB. If `/tmp/bundle_*` or `/tmp/xesim_*` dirs are obvious stale leftovers (older runs superseded by what we're about to launch), propose deletion before launching — silent process deaths, `BrokenPipeError` in pool workers, and disappearing output dirs are typical symptoms of a disk that filled mid-write. NEVER delete `bundle_v21_full_v2/` (visual-fidelity baseline). When in doubt, list candidates with sizes and ask.
